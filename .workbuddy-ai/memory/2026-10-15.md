### ★ 核心 bug：`errorCode == 0` 被误判成故障，拆掉了正常工作的推流管线

真机日志（首次跑通到编码器出帧）：

```
[自绘] 原生 HMI 已启动（1280x720 @ 60fps, 8294kbps）
[画面] 已开始产出（1280x720 @ 60fps）
CarHiNative: HMI 渲染已启动（GPU OnScreen 后端，零拷贝）   ← ★ GPU 后端真机可用！
CarHiNative: encoder output #1: size=29    flags=8 pts=0   ← SPS/PPS
CarHiNative: encoder output #2: size=29704 flags=2 pts=0   ← ★ 完整 I 帧 29KB
[画面] 错误([object ArrayBuffer]): 0                        ← ★ code=0 却被当故障
[自绘] 画面通路已停止                                        ← 管线自杀
推流已停止
```

**根因**：HarmonyOS 编码器在**正常出帧**的同时会回调一次 `onError(errorCode == 0)`。
`0` 是 `AV_ERR_OK`（成功），不是错误。但 ArkTS 侧**无条件**把任何 `onError` 当故障
→ `stopStreaming()` → 推流管线被拆掉 → **车机黑屏**。
这是「导航推过去」一直不成的直接原因。

**修复（两层防护，都已落盘）**：
1. `canvas_encoder.cpp` 的 `OnCodecError`：`errorCode == 0` 时只打一条 INFO 并
   `return`，**不冒泡**到错误回调。
2. `CarLifeEngine.ets` 的 `startStreaming` 错误回调：`code === 0` 直接 `return`，
   作为第二道防线，保证任何路径都不会误杀管线。

## 10:10-10:19 ★★ 真正根因抓到：帧回调错绑到 onError（args 下标写错），修复后导航帧真的推到车机了

### 推翻上午的 errorCode==0 理论

上午以为根因是「编码器 onError(errorCode==0) 伪错误」。clean 重装后真机复跑，
日志里 **`伪错误` INFO 出现 0 次** —— `OnCodecError(0)` 压根没触发过，理论不成立
（那两道 code==0 防线保留无害，但不是本案真凶）。

### ★ 真根因：napi_init.cpp `StartHmi` 把帧回调桥绑到了 args[2]

签名 `startHmi(options, onFrame, onError?)` → **args[1]=onFrame, args[2]=onError**。
但 686 行建 `g_frameTsfn`（call_js = CallFrameJs）时传的是 **args[2]**（即 onError），
694 行检测错误回调用的也是 args[2] —— 两个 tsfn 绑了**同一个 JS 回调**。

后果链（与真机日志逐条对上）：
1. 编码器每出一帧 → CallFrameJs → 调用 **errCb(ArrayBuffer, pts)**；
2. ArkTS 错误回调签名 (code, msg) 收到 code=ArrayBuffer、msg=pts=0 →
   打出 `[画面] 错误([object ArrayBuffer]): 0` —— **这就是那个悬案的来源**；
3. ArkTS 判定致命错误 → `stopStreaming()` → 管线自杀 → 车机 0 帧/黑屏。

**修复**：`args[2]` → `args[1]`（仅帧桥那一处），并在 ArkTS 错误回调加
`typeof code !== 'number'` 兜底（非数字=帧串进来了，只记日志不拆管线）。
`bash tools/build.sh clean` 全量重建（34 tasks executed），安装真机。

1. **`OH_AVScreenCapture_ResizeCanvas(capture, params_.width, params_.height)`**

2. **`OH_AVScreenCapture_SetCanvasRotation(capture, true)`**
   —— 让采集数据保持"正向"（rotation enabled, captured data remains upright）。
   手机横竖屏切换时，不设这个会导致采集数据带旋转标记、编码器按未旋转尺寸解读。
两者都做了失败降级（不致命时打 warn 继续）。

## ❌ 17:50 悬浮球方案判死（真机实测：装机失败）

### 实测结果
`ohos.permission.FLOAT_VIEW` 声明后 → **装机直接失败**：
```
code:9568289
error: install failed due to grant request permissions failed.
PermissionName: ohos.permission.FLOAT_VIEW
```

### 结论：鸿蒙的全局悬浮窗对第三方应用**完全关闭**
| 权限 | grantMode | availableLevel | 结果 |
|---|---|---|---|
| `SYSTEM_FLOAT_WINDOW` | system_grant | system_basic | ❌ |
| `USE_FLOAT_BALL` | system_grant | system_basic | ❌ |
| **`FLOAT_VIEW`** | user_grant | system_basic | ❌ **实测 9568289 装机失败** |

**关键教训**：`grantMode = user_grant` **不代表普通应用能用** ——
还要看 `availableLevel`。`FLOAT_VIEW` 是 user_grant 但 level=system_basic，
**声明即装机失败**（与 `CONTROL_DEVICE` 同一档待遇）。
★ 判断权限可用性要**同时看两个字段**：
  - `availableLevel == "normal"` → 普通应用可申请（如 ACCESS_SERVICE_NAVIGATION_INFO）
  - `availableLevel == "system_basic"` → 只有系统应用/预置应用（无论 grantMode 是什么）

### 已做处理
- 从 `module.json5` **移除** `ohos.permission.FLOAT_VIEW`
- `EntryAbility` 里注释掉 `tryShowFloatBall` 调用（保留代码备用）
- `core/FloatBall.ets` + `pages/FloatBall.ets` **保留**（若将来获系统授权可复用）

## 【第 N 轮】按大哥给的官方博客复查 Car Kit —— 结论：之前"Car Kit 判死"只对了一半

**触发**：大哥给了 https://developer.huawei.com/consumer/cn/blog/topic/03221788200932098
（《Car Kit 接入实战：从权限配置到导航流转闭环》），要求参考。

### ★★ 最重要的一条：`superLauncherCapability` 根本不存在

全项目 grep + 官方两处权威页面（`car-introduction`、`car-preparations`）交叉证实：

| 来源 | metadata 的 name 允许值 |
|---|---|
| Car Kit 简介（2026-08-03） | 只提**两个解决方案**：导航流转、超级桌面 |
| 开发准备「配置能力」（2026-09-09） | 原文：**「metadata 的 name 可选值：carHopCapability、hiCarCapability」** —— **只有两个** |

博客里 "metadata 加两个 name-value：carHopCapability / hiCarCapability" 与官方一致；
"超级桌面"（`smartMobilityType.SUPER_LAUNCHER`）是**状态枚举值**，不是 metadata 能力字段。
**即：超级桌面没有给生态应用留"声明我支持超级桌面"的元数据入口。**

### 超级桌面的真实准入门槛（推断，证据充分但未实测）

- 手机侧无需声明任何 capability，应用靠「手机与车机登录同一华为账号 + 超级桌面开关」
  被动出现在车机的中控屏「应用与服务 → 超级桌面」列表里
- 但**应用清单由华为维护**：官网有《超级桌面支持应用清单》**白名单**
  （HarmonyOS 4.X 是「支持清单」，5.X 变成「**不支持清单**」= 默认放行、逐个拉黑）
- 结论：**我们的 autoCar 要上车，需要华为侧把包名/应用纳入目录**，这是生态运营流程，
  **不是代码能解决的**。若大哥要在**鸿蒙智行/问界**上跑，唯一路径是联系华为走生态合作。
- 大哥的**安卓老车机没有超级桌面** → 这条路对他当前目标（CarLife 车机）本来也无效。

### 支线发现（对我们现有方案有实际意义）

1. `smartMobilityCommon` **没有**任何屏幕/画面/投屏接口：
   `SmartMobilityInfo` = `{status, type, data: Record<string,Object>}`，
   `data` 官方标注"由业务方自定义"，**没有文档化的 screenWidth/Height**。
   博客说的"获取车机的屏幕信息用于 UI 呈现"在 API 层**找不到对应入口**。
2. ★ **`getSmartMobilityStatus(HICAR)` / `on('smartMobilityStatus')` 我们可以正大光明用** ——
   `ACCESS_CAR_DISTRIBUTED_ENGINE` 是 **normal + system_grant**（已在 module.json5 里）。
   用途：**知道 HiCar 是否连着**。
3. ★★ **与大哥的"车机连接被 HiCar 抢"直接相关**：`status == RUNNING` 时
   说明 HiCar 已占住投屏通道 → 我们**不要启动录屏**、并给出明确的 UI 提示
   （"HiCar 正在使用车机，请先断开 HiCar 再启动 CarHi 投屏"）。
   这比现在盲目启动、然后卡在"切换中"要清楚得多。
4. HiCar 侧的 `getScreenWidth/getScreenHeight`（`com.huawei.hicarsdk.CarConfig`）是
   **Android 车机厂商 SDK**（devicepartner 文档线），**不是鸿蒙手机应用能用的**。排除。

### 与既有记载不冲突的部分

- `navigationInfoMgr` 的「无读取入口、只有上报/应答」**仍然成立**，本次未推翻。
  本次补上的只是：**"判死 Car Kit"这个更大的结论是错的** ——
  Car Kit 对生态应用开放的本来就是「流转」而非「取画面」，
  取画面从来归超级桌面/HiCar 管，而那两个不在开放 API 里。

`tools/build.sh` 里 `MODE="debug"` 是默认值，我们**每一轮真机验证跑的都是 debug 包**。
而官方 Car Kit《开发准备》第一句就是：

> 在打包应用时，请在 DevEco Studio 中…将编译模式修改为 "release"
> （博客补充：**debug 包下 Car Kit 的某些接口不会生效**，表现为 `801 Capability not supported`）

⇒ **「Car Kit 判死」这个结论有被 debug 前提污染的可能。** 这是个测试方法论漏洞。

### 已实测：release 包确实产出，且清单里真的不同

`bash tools/build.sh release` → BUILD SUCCESSFUL（9m20s，包 136MB）。
读 HAP 内 `module.json`（`zipfile` 直读，`unzip` 那 136MB 会超时）：

| 字段 | debug 包 | release 包 |
|---|---|---|
| `app.buildMode` | `debug` | **`release`** |
| `app.debug` | `true` | **`false`** |
| `app.apiReleaseType` | Release | Release |

★ **`apiReleaseType` 两边都是 Release，区分不出编译模式** ——
判据只能用 **`app.buildMode` / `app.debug`**（或运行时 `appInfo.debug`）。

### ★★ 顺带挖出一个更严重的 confound：能力声明**根本没配**

核对官方《开发准备·配置能力》，参与 Car Kit 需要**四件套**，我们只有两件：

| 要件 | 我们之前的状态 |

| 权限 `ACCESS_CAR_DISTRIBUTED_ENGINE` | ✅ 有 |
| skills `action.navigation.infoservice` | ❌ **缺** |

博客原文点明后果：**「metadata 的 carHopCapability / hiCarCapability 至少声明一个，
否则车机识别不到应用」**。

⇒ **2026-10-15 那次「双数据源零回调」的实测，不是一个公平测试** ——

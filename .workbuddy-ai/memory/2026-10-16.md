## 11. ★★★「投屏时切应用掉线」结案：App 侧无责（12:05–12:08 真机实测）

### 11.1 直接回答：切后台**不掉线**

受控实验（`uitest uiInput keyEvent Home` 切后台，带明确时间戳）：

| 时刻 | 事件 |
|---|---|
| 12:06:08.336 | `onBackground` ← 按 Home |
| 12:06:08.352 → 12:06:28.413 | `[心跳] 收到车机视频心跳 ×480 → ×580`（**连续，无中断**） |
| 12:06:15.252 / 12:06:25.260 | `[保活] 65563 已发送 ×50 / ×60（失败 0）`（**连续**） |
| 12:06:31.756 | `onForeground` ← 拉起 App |
| 全程 | **0 次 `通道 N 已断开`、0 次 `continuousTaskSuspend`** |

⇒ **23 秒后台窗口内，连接、保活、视频帧全部正常。**

### 11.2 真因：外部 peer 反复重连，服务端「新连接顶掉旧连接」

```
12:06:49.602 NETSTACK: Server accept new client, fd=73 clientfd=83
12:06:49.603 NETSTACK: js invoke TcpConnectionClose
12:06:49.606 CarHi: 通道 1 已断开
12:06:49.606 NativeScreenCapture: #837 OH_AVScreenCapture_StopScreenCapture
```

代码依据 —— `transport/ChannelServer.ets:118 handleConnection()` **有意为之**：
```ts
// 单通道只保留一个活跃连接（CarLife 语义：一条通道一个连接）
if (this.conn !== null) { this.closeConnection(); }
```

**因果链**：外部 peer 连入 → 服务端踢掉旧连接 → 7 条通道断开 → `engine.stop()` →
`source.stop()` → `[投屏] 采集已停止` → native 停止采集。
⇒ **采集停止是后果，不是原因**（之前读反了）。

**关键反证**：`12:06:49` 那次断开时 **App 已在前台**（12:06:31 起）⇒ 与前后台无关。

### 11.3 外部 peer 是谁

- 来自 `192.168.0.131` = **宿主机自己**。
- 自称 `samsung/SM-N9860` + `TQ2A.230505.002 release-keys`、请求 `1280x720@60fps`、
  `HU_INFO` **347 字节**。
- ⇒ **不是仓库里的 `tools/mock_hu.py`**：后者 `HU_INFO` 只有 **49 字节**、默认 **30fps**，
  真机解析出 `brand=` 是空的（实测日志：`[设备信息] 车机: brand=, model=, display=`）。
- 按不规则间隔（实测 17s / 27s / 80s）反复重连。

**副产品**：我起的 `mock_hu.py --duration 240` 只跑了 ~84 秒（发心跳 416 次）就被顶掉 ——
`Server accept new client` 一到，旧连接即被 close。

### 11.4 定位手法（记录备用）

`hdc -t <ip:port> shell "cat /proc/net/tcp"` → 解出 7 个端口的 `state=01` 对端 IP：
`7240=0x1C48 / 8240=0x2030 / 9240=0x2418 / 9241=0x2419 / 9242=0x241A /
9340=0x247C / 9440=0x24E0`。**一眼看出连进来的是谁。**

⚠️ 宿主机 `netstat -ano` 在本沙箱里**看不到**这些连接（连 hdc 自己的都查不到），

### 11.5 本轮推翻的两个自己的结论

1. 「AUDIO_RECORDING 名实不符 → 长时任务被挂起 → 切后台冻结」——**错**。
   前提（采集侧不采音频）本身不成立。
2. 「`[投屏] 采集已停止` = 采集被主动停掉」——**错**，因果读反。

**方法论教训**：**「A 发生在 B 之后」不等于「A 导致 B」。**

## 12. 自绘 vs 高德地图：能力归属核实（2026-10-16 晚，讨论稿）

**问题**：高德 SDK 的关键能力，对「自绘（native HmiRenderer）」与「直嵌+录屏」两条通路分别匹配多少。

### 12.1 核实到的硬事实（有出处）

- 地图渲染包名 = **`@amap/amap_lbs_map3d`**（`>=11.2.1`），配套 `@amap/amap_lbs_search`。
  **仓库根 `harmony/oh-package.json5` 现在只装了 `amap_lbs_navi` / `_common` / `_location`，
  没有 map3d** ⇒ 要直嵌地图，先加依赖。
- 地图组件名 = **`MapViewComponent()`**（官方「显示地图」页原文，2026-10-08 更新）。
  它就是普通 ArkUI 组件，可放进任意布局（含 `Stack`）。
  配套：`MapsInitializer.setApiKey(key)` →
  `MapViewManager.getInstance().registerMapViewCreatedCallback((mapView) => {...})` →
  `mapView.onCreate()` → `mapView.getMapAsync((aMap: AMap) => {...})`。
  拿到 `AMap` 后可 `setTrafficEnabled(true)`、加覆盖物、动 Camera。
- 官方地图页**只要求 `ohos.permission.INTERNET`**，无额外权限。
- 隐私合规：官方「显示地图」页**没写** `updatePrivacyShow`；
  但定位/导航 SDK 同构（`NaviSetting.updatePrivacyShow/updatePrivacyAgree`，
  本仓用法见 `AmapNaviBridge.ets:131-133`）⇒ 地图侧大概率也有同名静态方法，
  **装包后从 `.d.ts` 核实，别猜**。
- ★ `HmiRenderer::DrawMap()`（`hmi_renderer.cpp:1694-1732`）**画的是示意图**：
  网格线 + 一条**写死坐标**的折线 + 终点/车标圆点。**不是真地图**，也没有任何路网/瓦片数据。

### 12.2 能力归属（核心结论）

| 能力 | 归属 | 方案 A 自绘 | 方案 B 直嵌+录屏 |
|---|---|---|---|
| MapViewComponent / 夜景模式 / 导航态地图 / 自定义样式 / 离线地图 | map3d **渲染**侧 | ❌ 进不来 | ✅ 全有 |
| 红绿灯倒计时与灯色、路口放大图 | **只有渲染侧**（SDK 明说无结构化数据） | ❌ | ✅ |
| `AMapNavi` 结构化数据（路名/转向/剩余里程时间/红绿灯**数量**） | 纯数据 | ✅ **已有**（`AmapNaviBridge.ets`） | ✅ |
| `AMapNaviComponent` | ArkUI / **NavDestination 全页** | ❌ | ⚠️ 能挂但只能全页 |

⇒ **高德 SDK 的护城河在「渲染」，而自绘通路恰恰用不到渲染。**
⇒ 自绘路线下，高德只剩「算路 + 指令文本」；地图永远是示意图。

### 12.3 ★ 顺手否掉一条捷径（想绕开「车机画面 = 手机整屏」）

正路是只采**自己窗口**：`OH_CAPTURE_SPECIFIED_WINDOW = 2` + `videoCapInfo.missionIDs`
（头文件 `native_avscreen_capture_base.h:77-85` 枚举、`:243-248` 字段，确实存在；
我们代码里 `missionIDs = nullptr` 那个字段就是给它留的）。

**但整个 ArkTS API 面搜 `missionId` 零命中** ⇒ 第三方应用**拿不到自己的 missionID**
⇒ **指定窗口采集在本 SDK 上走不通**（除非系统权限）。

⇒ 结论：**只要走方案 B，就必须接受「车机画面 = 手机整屏」**：
手机得亮屏、常驻显示那一页、且不能被别的窗口盖住。

### 12.4 待办 / 阻塞项（按优先级）

1. 加 `@amap/amap_lbs_map3d` + `@amap/amap_lbs_search` 依赖，装包后从 `.d.ts` 核实
   ① 地图侧隐私合规方法名 ② 是否 `MapsInitializer.updatePrivacyShow` ③ Key 配置方式。
2. 真机实测：`OH_AVScreenCapture` 采**同进程自己的 `MapViewComponent`** 能否正常出帧
   （前台 + 切后台各一次）。
   ⚠️ 注意：**「原生 .so 能不能被采到」这个担心其实已有反证** ——
   我们此前已实测录到过**真实高德 App** 的画面（见 `MEMORY.md` §1.2 / §9），
   说明 `OH_CAPTURE_HOME_SCREEN` 采的是**合成后整屏**、不挑来源。
   真正的新变量是「**同进程自采**」，测的是这个。

## 13. ★「GPU 冻结 Bug」诊断 + 修复（2026-10-16 下午）

### 13.1 症状（真机实测，两轮复现）

**GPU OnScreen 后端只出首帧**，之后编码器再无输出，而 `OH_Drawing_SurfaceFlush` 一直返回 SUCCESS：

```
12:20:54.094  HMI 渲染已启动（GPU OnScreen 后端，零拷贝）
12:20:54.107  HMI 帧 #1 已提交，backend=gpu flushCode=0
12:20:54.114  encoder output #1: size=29    flags=8 pts=0   ← SPS/PPS
12:20:54.120  encoder output #2: size=23577 flags=2 pts=0   ← IDR
12:20:54.138  HMI 帧 #2 已提交，backend=gpu flushCode=0
12:20:54.164  HMI 帧 #3 已提交，backend=gpu flushCode=0
12:20:54.467  HmiRenderer stopped, frames=11                ← 11 帧只进了 1 帧
```

另一轮（跨天日志）：
```
★ 自愈触发：GPU 后端已提交 181 帧，编码器输出仍为 2（3006ms 无增长）→ 退 CPU 位图后端
```

设备 `/data/log/faultlog/` 里**没有**本应用的崩溃/AppFreeze 记录 ⇒ 排除系统级冻结。

### 13.2 根因（**推断**；能实测证明的只是"只出首帧"）

`OH_Drawing_SurfaceCreateOnScreen` 绑的是**屏幕（显示）窗口**；我们喂给它的是
`OH_VideoEncoder_GetSurface()` 返回的**编码器输入 producer 窗口**。
官方模块说明原文：「本模块为单线程模型策略，需要调用方自行管理线程安全和**上下文状态的切换**。」
症状（首帧能进、之后 flush 静默失效）与「该 API 不适用于 producer 窗口」吻合。

### 13.3 本轮改动（已 `bash tools/build.sh release` 通过）

`hmi_renderer.cpp` / `hmi_renderer.h`：

1. **`CreateBackend()` 的 AUTO 默认改为 CPU 位图**（不再"先 GPU 再退"）。
   GPU 降级为**显式可选**。理由：GPU 实测只出首帧，AUTO 先试 = 每次启动白冻 1.5s 再退，纯亏。
2. **自愈看门狗改为「持续生效 + 冷却」**：
   `healBudget = 2`（只在前 6 秒判 2 次）→ `kStallMs = 1500` + `kHealCooldownMs = 5000`。
   ★ 旧实现有个真实的洞：**用户 6 秒后手动切回 GPU、或 GPU 在 6 秒之后才停帧 → 永远救不回来**。
3. `hmi_renderer.h` 的 `BACKEND_AUTO` 注释同步。

⚠️ **副作用（重要）**：改后**自愈对显式 GPU 也生效** ⇒ 若大哥要"**固定用 GPU**"，
必须再把自愈对 `BACKEND_GPU` 关掉，否则 1.5 秒后又被切回 CPU。

### 13.4 待办

- 装机实测 **CPU 后端**在车机下发的 `1280x720@60` 下的真实帧率与 CPU 占用。
  **若够用 ⇒ GPU 这条路性价比不成立，可直接结案**（CPU 只是画卡片 UI，不是视频/3D）。
- 若不够：查"GPU 只出首帧"的根因（需真机迭代）。候选方向：
  ① 每帧 `SurfaceFlush` 返回值 + 编码器 input buffer 请求次数打点；
  ② 改 `OH_Drawing_SurfaceCreateFromGpuContext`（离屏 GPU surface）+ 读回 + `PushPixels` 上传；
  ③ 用 `OH_NativeImage` / `OH_ConsumerSurface` 中转。

### 用户诉求

### 关键技术结论（SDK 实证，非推测）
**用户判断正确：USB 与 WiFi 在协议层一致，手机端几乎不用改。**

核实三点：
1. `transport/ChannelServer.ets:99` 监听地址已是 `'0.0.0.0'`（所有网卡），
   USB 虚拟网卡上的连接**现在就能收到** —— 这是关键，省掉一大块工作。
2. 角色不变：手机始终 TCP 服务端，车机主动连（USB 下同理）。
3. SDK 权威证据（`@ohos.usbManager.d.ts`，API 14+，本工程 API 26）：
   鸿蒙**完整支持 USB Accessory 模式**：
   - `getAccessoryList()` / `hasAccessoryRight()` / `requestAccessoryRight()`
   - `openAccessory() -> USBAccessoryHandle.accessoryFd` / `closeAccessory()`
   - `USBAccessory{manufacturer, product, description, version, serialNumber}`
   注：`usbManager` 从 `@kit.BasicServicesKit` 导出（**不是** @kit.USBKit，后者不存在）。

### USB 下的两条可能路径（决定改造量）
| 路径 | 机制 | 手机端改造量 |
|---|---|---|
| 路 A：CDC-ECM/RNDIS | 车机把手机当 USB 网卡，双方各得 IP，跑 TCP | **零改造**（0.0.0.0 监听已覆盖） |
| 路 B：AOA 配件模式 | 无 IP 网络，字节流走 USB 批量端点 | **需新增 fd 字节流传输层**（工作量大） |

**两者改造量差一个数量级，必须实测分辨，不能猜。**

### 本轮实现：USB 诊断能力（只读，不改链路）
新增 `core/UsbProbe.ets`：
- `UsbLinkKind{NONE, IP_NETWORK, ACCESSORY, BOTH}`
- `probe()`：三路采集 —— ① Host 侧 `getDevices()`；
  ② `getAccessoryList()`（判路 B 关键）；③ `getAllNets()` + `getConnectionProperties()`
  列出全部网络接口含 IP（判路 A 关键，USB 网卡常见 usb0/rndis0/eth1）。
- 判定：有配件→ACCESSORY；有非 wlan/lo/rmnet 网卡→IP_NETWORK；都有→BOTH。
- `format()`：把结论拼成日志行。
- 注意：`getConnectionProperties` 是**异步**（Promise），必须 await。

`pages/Index.ets` 新增「USB 直连诊断」卡片 + `runUsbProbe()`：
显示链路形态（USB网络模式/配件模式/未检测到）、结论、网络接口列表，
按钮「诊断 USB」。用法：连线→车机启动 CarLife→点诊断。

## 项目：鸿蒙版 CarLife 手机端（E:/ZM/CarHi）

### 需求边界（大哥确认）

- 只做**手机端**，车机侧是**标准百度 CarLife 车机**，**车机系统 Android 4.4**（高德车机版跑不动）
- 范围：**只推导航画面（投屏模式）**，不做触控回传、不做车机遥控手机
- 音频走**蓝牙 A2DP** 独立通道，不实现 CarLife 音频通道
- 目标系统：**HarmonyOS NEXT**（ArkTS），开发机是**另一台装好 DevEco 的电脑**

### 关键发现（推翻前期假设）

**手机端是 TCP 服务端，车机是客户端。** 手机在 7240/8240/9240/9241/9242/9340/9440
七端口**监听**，车机主动连。→ **不需要 USB 从设备模式**，前期判断「可能堵死」的路完全绕开。

### 已排除的路（有依据）

- **后台导航模式**（`MD_NAVI_NEXT_TURN_INFO` 65584）：参考实现里只有消息 ID 和名称，
  **Proto 字段结构不存在**；且需要车机端有地图引擎渲染，安卓 4.4 老车机不具备
- **复用第三方导航 App 数据（A 类）**：鸿蒙无公开 API 读其他 App 状态；
  无障碍读屏不可靠（界面图标化、地图 App 升级即失效）
- **HiCar 那套做法**：高德是**主动适配** HiCar SDK（官方文档：地图应用"非公开，需合作后开放权限"），
  我们没有那个生态位，复制不了

### 协议真值源

`refs/carlife_pc_tool/`（2026-09 新项目，逆向自真实车机端 carlife-vehicle）
- 全大端序；**Ch1/6 头 8 字节，其他通道 12 字节**
- 负载 Protobuf，包名 `com.baidu.carlife.protobuf`
- 视频：**H.264 裸流（NALU）**，消息 ID 131073，无额外封装
- 心跳 1000ms
- 每段代码都带百度官方混淆源码行号溯源

### 实测验证结果（非推测，可复跑）

| 项 | 结果 |
|---|---|
| 消息编码字节级对拍（vs Google 官方 protobuf） | **16/16 通过** |
| 握手方向互补校验 | **5/5 通过** |
| 常量一致性（62 个消息 ID + 8 个端口） | **全部一致** |
| 引用完整性 | **无问题** |

**重要认知（踩过一次坑）**：proto2 的 optional 字段，**显式赋零值会编码，不赋值则跳过**。
第一轮对拍 6 项失败就是因为我让 Python 侧显式传了 `minorVersion=0`/`authenResult=False`
这类零值，产生了 presence 语义。**两边行为都正确，是基准构造有误导性。**
修正基准后全通过。以后构造 PB 基准要区分「未设置」与「显式设为零值」。

## USB 直连诊断 —— 结论：AOA 配件模式（路 B）

### 实测证据（本机 + 真机 hdc）

**1. 应用侧诊断（`UsbProbe.probe()`，大哥在真机上点的）**
- 结论：`UsbLinkKind.ACCESSORY` = 2
- 摘要原文：`USB 配件模式(AOA)：检测到配件但无独立网卡，需新增 fd 字节流传输层（工作量较大）`
- 网络接口只列出：`rmnet0 [10.206.64.74/32 2408:8453:...]`

**2. 内核侧地面真值（`hdc shell ifconfig -a`，绕开 App API 的不确定性）**
```
全部网卡: CPU0 Hisilicon0 ancowlan0 chba0 dummy0 ifb0 ifb1 ip6_vti0 ip6tnl0
          ip_vti0 lo nan0 p2p0 rmnet0..rmnet_emc1 rmnet_ims00.. rmnet_tun00..14
          sit0 wlan0 wlan1
带 inet 的: lo 127.0.0.1 | wlan0 192.168.0.186 | ancowlan0 172.17.1.1
路由表: 172.17.1.0/24 dev ancowlan0 ; 192.168.0.0/24 dev wlan0
```
★ **没有任何 USB 虚拟网卡**（无 usb0 / rndis0 / eth1）→ **路 A（CDC-ECM/RNDIS）被排除**。
  这与「配件模式无 IP 网络」的预期完全吻合，互为佐证。

**3. SDK 侧能力核实（`@ohos.usbManager.d.ts`，DevEco 26.0.0 内嵌 SDK）**
```ts
getAccessoryList(): Array<Readonly<USBAccessory>>;          // @since 14
hasAccessoryRight(a): boolean;                              // @since 14
requestAccessoryRight(a): Promise<boolean>;                 // @since 14
cancelAccessoryRight(a): void;
openAccessory(a): USBAccessoryHandle;                       // 抛 14400001 需先 request
closeAccessory(h): void;
interface USBAccessory { manufacturer; product; description; version; serialNumber }
interface USBAccessoryHandle { accessoryFd: number }
```
- 以上接口 **均无 `@permission` 标注** → 不需要在 module.json5 额外申请权限。
- 文档原话：「opens the accessory file descriptor. Then … communicate … through the
  **read** and **write** APIs provided by Core File Kit」→ 用 `@kit.CoreFileKit` 的 `fileIo`。
- `fs.read(fd, buffer, options?) => Promise<number>`（异步，libuv 线程池，不阻塞 JS 线程）。
- 相关错误码：14400001 未授权 / 14401001 配件不匹配 / 14401002 打不开节点 / 14401003 不能重开。

### 本轮新增能力：`UsbProbe.tryAoa()` + 界面「AOA 试连（读原始流）」按钮
- `tryAoa()`：getAccessoryList → has/requestAccessoryRight → **真的 openAccessory() 拿 fd**
  → 试读最多 256 字节（与 1500ms 超时 Promise 赛跑，读不到就收手）→ 无论成败都 closeAccessory()。
- 目的（一次实验回答两件事）：
  ① 配件是**真的**还是 `getAccessoryList()` 的假阳性 → 决定要不要写传输层；
  ② **AOA 单字节流上的封包格式**（见下）。
- `probe()` 保持**只读**语义不变，AOA 试连单独一个入口，两者不混。

### ★ 关键未知：AOA 单流上的通道复用格式（必须先实测，不能猜）
- 已核实的 TCP 侧事实：**帧头里没有通道号**，通道由 **7 个 TCP 端口**隐含：
  7240(CMD/1) 8240(VIDEO/2) 9240(AUDIO/3) 9241(TTS/4) 9242(VR/5) 9340(TOUCH/6) 9440(DATA/7)。
  帧格式：Ch1/Ch6 = `[u16 len][u16 reserved][u32 service_type]`；其余 = `[u32 len][u32 seq][u32 service_type]`。
- AOA **只有一条字节流**（一对 bulk 端点），7 个逻辑通道必须靠某种方式复用。
  **这是写传输层前必须拿到的事实** —— 猜错等于白写。
- 参考实现 `refs/carlife_pc_tool`（逆向自车机端 APK）**帮不上这个忙**：它的 USB 模式走的是
  `adb forward tcp:PORT tcp:PORT`（端口穿透），**不是 AOA**，所以它没有 USB 封包格式。
- 权威源 `refs/OFFICIAL_PROTOCOL.md` **本机没有**（只在另一台机器）；官方 APK 反编译产物
  `/tmp/carlife_src`、车机端 APK 本机也都没有。

## Wi-Fi Direct（WLAN 直连）可行性调研（10:10）

**问题**：鸿蒙 7.0 上如何手工连接 Wi-Fi Direct。

**结论：设置界面已无此入口，手工连不了；协议与 API 仍在，只能代码实现。**

证据链：
1. **华为官方支持页**（consumer.huawei.com/cn/support/content/zh-cn15922542）：
   "首发 HarmonyOS 3.0 之后的产品将均取消 WLAN 直连功能，**HarmonyOS 5 之后的产品均取消
   WLAN 直连入口**"；同页另一句："**所有华为手机/平板均支持 WLAN 直连协议即 Wi-Fi Direct**"。
   → 入口移除，协议保留。
2. **真机 syscap 实测**：MRT-AL10 / 7.0.0.109(SP6C00E105R8P2) / API 26 的
   `/system/etc/syscap.json` **含 `Communication.WiFi.P2P`**（另有 AP.Core / Core / STA）。
3. **真机设置应用实测**：`bm dump -n com.huawei.hmos.settings` 共 39 个 Ability，
   **无任何 p2p / direct / wlan 命名页面** → 设置 UI 确实没有直连入口。
4. **SDK 契约**（`DevEco/sdk/default/openharmony/ets/api/@ohos.wifiManager.d.ts`）：
   `startDiscoverDevices` / `stopDiscoverDevices` / `p2pConnect` / `p2pCancelConnect` /
   `createGroup` / `removeGroup` / `getP2pLinkedInfo` / `getCurrentGroup` /
   `getP2pPeerDevices` / `getP2pLocalDevice` —— **全部无 `@systemapi` 标注**，
   权限一律 `ohos.permission.GET_WIFI_INFO`。
5. **权限级别**（OpenHarmony `security_access_token` 的 permission_definitions.json）：
   `GET_WIFI_INFO` = `availableLevel: normal` / `acl: NORMAL` → **三方应用可申请**。
   对照：`MANAGE_WIFI_HOTSPOT` 是 `system_core` + SYSTEM，三方拿不到。

**⚠️ 未实测**：第 5 条查的是 **OpenHarmony 主干**权限定义，非华为 HarmonyOS 商用版；
"三方 App 真能调通 P2P" 属**静态推断**（SDK 契约 + 权限级别），**尚未在真机跑通**。

**对 CarHi 的提醒**：Wi-Fi Direct 建组后是独立 P2P 网段（GO 通常 192.168.49.1），
车机端 CarLife App 是否会在 P2P 网卡上监听**未知**。无路由器的"直连"更稳的路子是
**手机开热点 / 车机开热点**（常规 STA/AP），不是 Wi-Fi Direct。

**真机地址更新**：`hdc list targets` → `192.168.0.186:44793`
（旧的 `192.168.31.126:38957` 已失效，端口会变，别写死）。

## ★★ Wi-Fi Direct 连上车联盒子 QH3002 —— 已打通（10:26 实测）

**结论：鸿蒙 P2P API 三方确实可用（真机实测，不再是静态推断），已成功连上盒子。**

## 2026-10-13（四）触控注入的权限现实：`CONTROL_DEVICE` 走不通

### ★ 先纠正我自己的错
我先前说「需要 `INJECT_INPUT_EVENT`」—— **权限名说错了**。真实权限是
**`ohos.permission.CONTROL_DEVICE`**（SDK 里全 14 处引用都落在 `inputEventClient` 一个模块）。
API：`@kit.InputKit` → `inputEventClient.createTouchController()` → `touchDown/touchMove/touchUp`，
`@since 26.0.0`（正好本机 API 26），**不是 `@systemapi`**，`@stagemodelonly`。

### 结论：普通应用拿不到，且**手机上根本用不了**
三条硬证据（官方文档 + 51CTO 真机实测文 `ost.51cto.com/posts/59151` 互证）：

| 项 | 值 | 后果 |
|---|---|---|
| `grantMode` | **`manual_settings`**（既非 `system_grant` 也非 `user_grant`，全机 881 条里只有 4 条） | 声明后**装机直接失败**：`code:9568289 install failed due to grant request permissions failed` —— **整包装不上**，不是"权限没给" |
| `deviceTypes` | **`["2in1"]`** | **只在 2in1 登记**；手机上调用 `createTouchController()` 直接回 **`801 Capability not supported`** |
| `availableLevel` | `system_basic`，`availableType=NORMAL`（不在 ACL 白名单，但也**不承诺能拿到**） | 需系统应用/系统签名路线 |

- 四个授权口**全不通**：`requestPermissionsFromUser` → 静默返回 `authResults=2, dialogShown=false`
  （**不抛异常**，且 `2` 不在 `GrantStatus` 枚举里，判 `=== PERMISSION_DENIED` 判不中）；
  `requestPermissionOnSetting` → 抛 `12100014 cannot be requested from the user`；
  `openPermissionOnSetting` → 抛 `12100001`；`getSelfPermissionStatus` → `INVALID(2)`。
- ⚠️ **`canIUse('SystemCapability.MultimodalInput.Input.InputSimulator')` 在手机上也返回 `true`** ——
  骗人的，拦不住（该 syscap 是 12/13 代登记的老能力位，覆盖 phone/tablet/2in1）。
- 官方文档原文旁证：「设备行为差异：该接口**仅在 PC/2in1 设备中可正常调用**」。
- 声明 `manual_settings` 权限还要求 `reason` + `usedScene`，缺了构建期报 `00303218`。

### 替代路径：无障碍（AccessibilityKit）—— 这条路是通的
- `AccessibilityExtensionAbility`（**未弃用**）+ `AccessibilityExtensionContext`。
- 注入接口：**`injectGestureSync(gesturePath: GesturePath): void`**（`@since 10`，
  `@syscap SystemCapability.BarrierFree.Accessibility.Core`，**无 `@permission` 标签**）。
  数据结构：`GesturePath{ durationTime: ms, points: GesturePoint[] }`，
  `GesturePoint{ positionX, positionY }`（px）。
- 授权模型：**用户手动在「设置 → 无障碍」开启服务**即可，**不需要 root、不需要系统签名**。
- 配置：`module.json5` 的 `extensionAbilities[]` 里 `"type": "accessibility"` +
  `metadata` `"ohos.accessibleability" → "$profile:accessibility_config"`；
  `resources/base/profile/accessibility_config.json` 里
  `accessibilityExtensionTypes: ["viewAttributes", "gesture"]`（**`gesture` 是关键**）。
- ⚠️ **待实测的不确定点**：SDK 里 `injectGestureSync` 标了 **`@deprecated since 12` 且未给 `@useinstead`**。
  deprecated ≠ removed，但**必须真机实测确认在 API 26 上还能不能注入**，别当成已验证结论。
- 架构注意：AEA 跑在**独立进程**，主 Ability 拿到的触控坐标要跨进程送给它
  （commonEvent / socket / rpc 任选），这是接入时的主要工作量。
- 另一条路：设备侧 `hdc shell uitest uiInput click`（我们现在点屏幕就是这么干的），
  但**需要 PC 常连** —— 车里没有 PC，对 CarLife 场景不适用。

### ★ 故障现象与真因：「接口全通了，一会就断了」
**现象**：7 条通道全连上、握手全套走通（含 65609），但「切应用」后推流停掉。
**真因**（设备侧 hilog 实锤，两行只差 10ms）：
```
15:43:59.328  onBackground                            ← 切到后台
15:43:59.338  [编码] 错误(10): video encoder error     ← 10ms 后编码器崩
15:43:59.339  检测到可恢复中断，2s 后重试（第 1/5 次）
15:43:59.388  第 1/5 次  ← 重复！
15:43:59.396  第 2/5 次   ┐
...                       ├ 全部发生在 100ms 内！
15:43:59.429  第 5/5 次   ┘
15:43:59.439  已连续重试 5 次仍失败，停止推流
```
**根因不是分辨率**（车机下发了 1280x720@60，覆盖了默认值）。是三个 bug 叠加：

| # | Bug | 说明 |
|---|---|---|
| 1 | **切后台中断屏幕采集** | 鸿蒙安全设计：**长时任务只保「进程不被冻结」，不保「采集不被中断」**。即使 `AUDIO_RECORDING` 已生效（日志「长时任务已生效（仅采屏）」）也照断。 |
| 2 | **`OnCodecError` 无节流** | `screen_encoder.cpp:67` 直接 `EmitError`。底层进错误态后**高频重复回调** → 100ms 内穿透 6 次。 |
| 3 | **重试机制失效** | `scheduleRetry()` 的防叠加只挡定时器、**不挡 `retryCount++`** → 计数被高频错误推到 5，而 `attemptRecover()` **一次都没执行过**。现象即「说 2s 重试，实际 9ms 连爆」。 |

### 修复（已编译通过 + 已装真机）
1. **错误冷却去重**：新增 `lastCodecErrorAt` / `codecErrorBurstCount` /
   `CODEC_ERROR_COOLDOWN_MS = 1000`。同一波错误在冷却窗内**只决策一次**
   （取 1000ms：> 爆发时长 ~100ms，< `RETRY_DELAY_MS` 2000ms，不会误合并两次真实中断）。
2. **`attemptRecover()` 开头重置冷却状态**，避免上一波残留影响下一波。
3. **★ 恢复成功后 `retryCount = 0`**（原代码 `restartCapture()` 成功直接 return，
   配额不重置 → 历史消耗累积，下次真中断可能配额见底直接放弃）。

### 关键认知（重要）
**不要试图「避免切后台中断采集」—— 那是鸿蒙的安全设计，做不到。**
正确策略是 **「中断后必须能恢复」**。本次三个修复都是围绕这一点。

## ★★ 2026-10-13（九）推流真因定位 —— 「编码器尺寸配错」把车机搞崩

### 大哥给的两条关键事实（推翻了我此前的多个结论）
1. **官方 CarLife 切后台画面继续、不掉线**（大哥亲眼验证）→ 说明「切后台必中断」是**伪命题**。

   而且**「车机端会崩溃」**（不是手机崩）—— 这是全新的、决定性的信息。

### ★ 我此前三个错误结论（必须记住，别再犯）
| 错误说法 | 真相 |
|---|---|
| 「切后台中断采集是鸿蒙安全设计，做不到避免」 | **错**。华为官方博客原话：应用退后台超 3 秒被挂起影响「屏幕录制」，**长时任务就是为此提供的**。能做，看实现。 |
| 「code=10 是未知错误 / AV_ERR_UNKNOWN」 | **错**。`AV_ERR_UNKNOWN=6`；**`10 = AV_ERR_INPUT_DATA_ERROR`（输入数据错误）**，含义很具体。 |
| 「日志显示采集没报状态变化」 | **前提就错了**。native 侧 tag 是 **`CarHiNative`**，此前只过滤 `CarHi` → **整条 native 通道根本没在听**。 |

### ★★ 真因：VirtualDisplay 尺寸配错 → 编码器零输出 → 车机硬解器崩溃
**实测数字（全部是硬证据）**：
```
手机物理屏（RenderService 实报）: 1272 × 2860   ← 竖屏！不是 1920×720
车机下发 98311 期望            : 1280 × 720
我们配给 VirtualDisplay 的值    : 1280 × 720   ← 错在这里
```

**完整因果链（设备侧 hilog 实证）**：
```
① VirtualDisplay 配 1280×720，但物理屏 1272×2860 → 两者不符
② 编码器**一帧都编不出来**（实测 8.7 秒零输出，持续 code=10）
③ 手机只发了 SPS/PPS 配置头，没有任何帧数据
④ 车机按 SPS 声明备好解码器，却永远等不到帧 → **硬解器崩溃 / 车机 App 崩溃**
⑤ 现象 = 「一切应用就崩」「横屏也崩」，与切哪个 App 无关（必现）
```

**为什么官方不崩**：官方按手机**真实屏幕尺寸**编码，车机拿到尺寸正确的流，自己缩放到它的显示区。

### ★ 大哥确认的两个关键事实
- 「真机屏幕 1920×720 横屏」= **车机上显示的尺寸**（车机缩放后的），**不是手机屏幕**。
- 「手机横，车机就横」→ 手机画面是原样推过去的，车机自己适配。

### ★ SDK 里就有正解（`native_avscreen_capture.h`）
- 鸿蒙采集底层本来就是**往 VirtualDisplay 渲染再采集** —— 「虚拟桌面推送」不是能不能做，而是**本来就是这个机制**。
- `OH_AVScreenCapture_ResizeCanvas(capture, w, h)`（@since 12）—— 官方头文件原话：
  「**设置屏幕采集数据的分辨率**……调用方与视频数据消费者**必须确保支持接收视频数据的分辨率变化**」
  → 这句就是我们 bug 的正面描述：分辨率变了，编码器侧也得跟着变，我们没做。
- `OH_AVScreenCapture_StrategyForCanvasFollowRotation(strategy, true)`（@since 20）：
  「旋转后自动调整 **VirtualDisplay 尺寸**」。本项目**已开**（日志见 `followRotation=true`），
  但**初始 VirtualDisplay 尺寸本身就是错的**，所以照样崩。

### 修改（本轮）
1. 🆕 `core/ScreenSizeProbe.ets` —— 取手机真实屏幕尺寸（`display.getDefaultDisplaySync()`，无权限要求），
   提供 `get()`（原样）与 `getLandscape()`（保证宽>高）。

**`1272 × 2860`**（竖屏）。此前 memory 里记的「1920×720 横屏」是**车机端显示尺寸**，已更正。

- 编码器 **起来了**（stage=0，无 stage 2、无 code=10）—— vp/px 修复生效。
- 但 mock HU 仍报 `VIDEO 收 0 帧`，日志里 **`encoder output #N` 一条都没有**。
- 即：**编码器在跑，但一帧输入都没收到。**

### 根因：A2 的机制本身不成立（不是 bug，是路子错）

查遍 SDK 头文件（`external_window.h` / `native_interface_xcomponent.h` /
`native_image.h`）后的结论：

**Surface 模式的数据流是「消费者持有 surface，生产者往里写」。**
- 编码器 = 消费者，它用 `OH_VideoEncoder_GetSurface()` 拿到**自己的**输入 surface。
- XComponent = 生产者，它渲染进**自己的** surface（`getXComponentSurfaceId()` 给的那个）。

**两个 surface 是两口井。** 现有 `AttachSurface()` 做的事是
「把 XComponent 的 surfaceId 换成 OHNativeWindow 并持有引用」——
这**没有在两者之间建立任何数据通路**，只是拿了个句柄。所以帧永远为 0。

**关键否定证据（关键 API 都不存在）：**
| 我们想要的 | OHOS 是否有 | 证据 |
|---|---|---|
| 把外部 surface 塞进编码器当输入 | ❌ 无 | 只有 `OH_VideoEncoder_GetSurface` 拿它自己的 |
| 让 XComponent 渲染到指定外部 surface | ❌ 无 | `OH_ArkUI_XComponent_GetNativeWindow` 只能**读**它自己的 window；`XComponentSurfaceConfig` 只配 opaque 等属性 |
| 把 XComponent 的 window 直接喂给编码器 | ❌ 无 | 没有「替换编码器输入 surface」的 API |

**唯一成立的机制（官方文档口径，cnblogs/Surface模式解析）：
「相机拍视频：编码器提供 Surface，相机直接写入，编码器直接读取」
—— 生产者必须往编码器的 surface 里写。**

### 由此得到的真实可选路径

| 代号 | 做法 | 可行性 | 评价 |
|---|---|---|---|
| **A1** | 用 **EGL/GLES 直接把界面画进编码器的输入 surface**（`OH_VideoEncoder_GetSurface` → `OH_NativeWindow_GetSurfaceId(encoderSurface)` → 在该 id 上建 EGLSurface）。 | ✅ 官方正道 | 性能最好；画复杂 UI 全靠手写 GL，**很费劲** |
| **β** | ArkUI 正常渲染 XComponent；每帧把它 window 的内容**拷进**编码器 surface（`OH_NativeImage` / `OH_ConsumerSurface_Create` 做中转，或 `OH_NativeWindow` acquire-release 拷贝）。 | ✅ 可行 | 保留 ArkUI 开发效率；代价是**每帧一次 GPU 拷贝**（2860×1174 RGBA ≈ 13MB/帧 ×30fps）。个人自用可接受 |
| γ | 把 XComponent surfaceId 交给编码器 | ❌ | **就是现在这条，机制不存在** |

### 关键 API 记录（后续要用）

- `OH_NativeWindow_GetSurfaceId(OHNativeWindow*, uint64_t*)` — external_window.h:742
- `OH_NativeWindow_CreateNativeWindowFromSurfaceId(uint64_t, OHNativeWindow**)` — :763
- `OH_ArkUI_XComponent_GetNativeWindow(OH_ArkUI_SurfaceHolder*)` — native_interface_xcomponent.h:1625（API 19+，**只读**该 XComponent 的 window）
- `OH_NativeImage_Create/ AcquireNativeWindow / GetSurfaceId / UpdateSurfaceImage / SetOnFrameAvailableListener` — native_image/native_image.h
- `OH_ConsumerSurface_Create()` — native_image.h:342（API 12+）
- `OH_NativeXComponent_GetXComponentSize(...)` — :677

### 另一处已发现的**独立**缺陷（无论走哪条路都得修）

`CanvasFrameSource` 现在**故意**用「画布实测像素」(2860×1174) 当编码尺寸，
理由是旧录屏方案的注释（"画布尺寸必须等于编码器输入尺寸"）。**路线 A 下这条是错的**：
- 车机协商的是 **1280×720**，它会按 1280×720 解码；
- 我们编码 2860×1174 → 即使帧通了，车机也是花屏/裁切；
- 正确做法：**编码尺寸 = 车机期望尺寸（1280×720）**，
  画布按 1280×720 开（或画大后缩放进编码器 surface）。

→ 结论：**A2 的"surfaceId 交给编码器"路数走不通，需在大哥确认后改走 A1 或 β。**

## （十三）★ 最小验证实测：EGL 建到了编码器 surface 上，但 eglSwapBuffers 失败 0x12291

### 关键进步（probe2，17:44）

```
✓ 编码器已启动 1280x720
✓ 编码器输入 surface id = 6781753360636
EGL: 已取到 EGL_PLATFORM_OHOS_KHR display
EGL 1.4 已初始化
[步骤] eglChooseConfig OK
[步骤] eglCreateContext OK
[步骤] eglCreateWindowSurface(encWin)...      ← 传的是 OHNativeWindow* 指针
EGLSurface 结果：成功 err=0x12288              ← ★ EGLSurface 建成功了！
[步骤] eglMakeCurrent...                       ← ★ current 也成功
✓ EGLSurface 已建立并 current
GL_VERSION=OpenGL ES 3.2 B312.c42a19c9...
[步骤] 首帧 glClear 完成，准备 eglSwapBuffers...
eglSwapBuffers 失败 err=0x12291                ← ★ 卡在这里
画第 1/30/60/90 帧：swap=0 编码器已出帧=0
❌ 机制不通：画了 0 帧但编码器一帧没出
```

### 两个重要修正（已改代码）

1. **`reinterpret_cast<EGLNativeWindowType>(surfaceId)` 会让进程直接挂掉** ——
   无异常、无 crash 日志、`ps` 里进程消失。**必须传 `OHNativeWindow*` 指针**
   （即 `OH_VideoEncoder_GetSurface` 给的 encoderSurface_）。
   改掉之后进程存活。
2. `EGL_RENDERABLE_TYPE` 用 **`EGL_OPENGL_ES2_BIT`**（本机 EGL 只报 1.4，
   ES3_BIT 可能被拒）；ES2 config 建 ES3 context 没问题（实拿 ES 3.2）。

### 当前卡点：`eglSwapBuffers` err=**0x12291**

- `0x3000`(12288)=EGL_SUCCESS；`0x3001`(12289)=**EGL_NOT_INITIALIZED**。
  → `0x12291` = 12289 = **EGL_NOT_INITIALIZED**。
- 含义：surface 句柄建出来了，但**没有可交换的后备 buffer / display-surface
  配对不成立**。典型成因：
  - 编码器的输入 surface 不是「直接当 EGL window 用」的用法；
  - 或该 OHNativeWindow 还没连上 buffer allocator / 没设 geometry；
  - 或 EGLDisplay 与这块 surface 不属同一 platform 实例。

### 下一步要做的隔离实验（判断是 EGL 本身的问题，还是这块 surface 特殊）

- **对照组**：拿一个「已知可用」的 window（比如 XComponent 的 window，
  或自己 `OH_NativeWindow_Create` 一块）建 EGLSurface + swap，看是否也 0x12291。
  - 若对照组也失败 → EGL 用法/参数问题（可能缺 EGL 配置或需 `eglSwapInterval`）。
  - 若对照组成功、只有编码器 surface 失败 → 说明「编码器输入 surface 不能当
    EGL window 直接画」，那 A1 这条路也要重新想（比如用 OH_NativeImage 中转）。

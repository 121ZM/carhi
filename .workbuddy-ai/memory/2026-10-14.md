## ★ 原理说明：CarLife 官方是怎么做到「后台也能推」的
- 大哥问「carlife 是怎么做到的」——这里把根本差异记清楚，它是选路线的依据。
- ### 官方 = Native GL 自绘
  ```
  应用自己创建 Surface → GL 上下文绑上去 → 所有 UI 用 GL 绘制
       → 编码器输入 = 同一块 Surface → MediaCodec 直接读该缓冲区编码
  ```
  本质同「游戏引擎推流」：**UI 绘制与视频编码消费同一块 GraphicBuffer**。
  三大天然优势：① 不受前后台影响（GL 循环是应用自己的线程）② 零拷贝 ③ 帧率自控。
- ### 我们不能照抄的根本原因
  | | 官方 | CarHi |
  |---|---|---|
  | 界面绘制 | OpenGL ES（自己画） | **ArkUI 声明式**（系统画） |
  | 渲染线程 | 应用自己的 GL 线程 | 系统渲染线程 |
  | 目标缓冲区 | 自己创建的 Surface | 系统分配的 Surface |
  | 切后台 | 照跑 | **系统停掉绘制** |
  → **ArkUI 的渲染权在系统手里**：拿不到 buffer、控制不了生命周期。
  → 矛盾本质：ArkUI 开发效率高 vs GL 自绘完全可控，二者不可兼得。
- ### 三条路（再次确认）
  - **A1** 照抄官方 = 整个 HMI 重写成 GL 绘制。代价**极大**（要自己实现中文文字渲染、
    图片解码、布局引擎 ≈ 写个迷你 UI 框架）。
  - **β** 离屏快照 = UI 代码不动，`createFromBuilder` 后台离屏渲染 → 拷进编码器 surface。
    两道坎：① 能否 <33ms/帧 ② 每帧一次「渲染→读像素→写 buffer」搬运。
  - **混合** = 主界面 β + 地图等延迟敏感部分 GL。
- **当前正在验证 β**（设置页「离屏渲染测速」按钮，已装机）。这个数字决定最终选路。

### 解法：把渲染器从编码器上解耦 —— `runHmiSelfCheck`

- **纠错**：上一轮我写的 `OH_Drawing_ImageEncodeToFile(...IMAGE_FORMAT_PNG...)`
  **根本不存在**。全量 grep `native_drawing/*.h` 无 `EncodeToFile` / `ImageFormat` / PNG；

- **改法**：native 只把 **RGBA8888 裸像素**通过 `std::function` 回调交出来，
  ArkTS 侧 `createPixelMapSync` + `ImagePacker.packToData({format:'image/png'})`
  落盘到 `getContext().filesDir`。这条路是官方既有能力。
- 实现位置：`hmi_renderer.h/.cpp` 的 `RunSelfCheck(w,h,cb)`（CPU 位图后端、**同步**、
  **不开线程**、**不碰编码器**）；`napi_init.cpp` 的 `runHmiSelfCheck` 导出
  （用**独立的** `HmiRenderer probe` 实例，绝不碰 `g_hmi`）；
  ArkTS 侧 `NativeHmiSource.ets` 的 `runHmiSelfCheck()` + `dumpPng()`。
